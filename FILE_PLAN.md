**Two real bugs found and fixed while building this, both worth flagging explicitly:**

1. **Tenant-isolation gap in `UserController`/`RoleController`.** Both assumed `TenantContext` is always bound. A Super Admin (platform user, `school_id` null) legitimately has `users.view`/`roles.view` permissions for platform purposes, but nothing stopped that same token from hitting the *school-scoped* `/api/v1/users` or `/api/v1/roles` endpoints — where a null tenant id meant `where('school_id', null)`, which for roles would have matched **the platform's own `Super Admin` role** (also stored with `school_id = null`). Fixed by adding `TenantContext::assertBound()` (throws 403), called at the top of every action in both controllers. Covered by `RoleManagementTest::test_super_admin_cannot_manage_roles_through_the_school_scoped_endpoint`.

2. **Spatie/Sanctum interaction bug, not our code, but our problem to work around.** `Role::users()` resolves its target model via `getModelForGuard($this->attributes['guard_name'] ?? config('auth.defaults.guard'))`. `withCount('users')`/`loadCount('users')` build that relation against a template (unsaved) `Role` instance with no `guard_name` attribute yet, so it always falls through to `config('auth.defaults.guard')`. Laravel's `auth:sanctum` middleware calls `Auth::shouldUse('sanctum')` as a side effect of authenticating, which **overwrites that same config key for the rest of the request**. `'sanctum'` isn't a normal provider-based guard, so `getModelForGuard('sanctum')` returns `null`, and the relation crashes with `Class name must be a valid object or a string`. Every role-listing/count call under Sanctum auth would have 500'd. Fixed with `App\Support\Tenancy\RoleUserCount`, which counts via a direct `model_has_roles` pivot-table query instead of the relation. Applied to both the API and web controllers for consistency, even though the web portal (session auth) doesn't trigger the guard mutation itself.

**A second, more serious tenant-isolation bug found and fixed here** (beyond the two from Phase 1c): Laravel's `SubstituteBindings` middleware — which resolves route parameters like `{student}`, `{class}` into Eloquent models — runs **before** custom route middleware in Laravel's default priority order, regardless of the order listed in a route group's `middleware([...])` array. Since `BelongsToTenant`'s global scope depends on `TenantContext` being set by our `IdentifyTenant` middleware, every implicitly-bound tenant-scoped model (`Student`, `SchoolClass`, `Stream`, `AcademicYear` — anything using the trait) was resolving **unscoped** at binding time: a school admin could be handed any other school's record just by knowing/guessing its numeric id, even though the exact same query later in the controller would have been correctly scoped. Confirmed via a failing test (`school_admin_cannot_view_or_update_another_schools_student`) before the fix. Fixed at the root, once, for every current and future tenant-scoped controller: `bootstrap/app.php` now calls `$middleware->prependToPriorityList(before: SubstituteBindings::class, prepend: IdentifyTenant::class)`. Re-ran the entire suite (including Phase 1/1c tests, which use explicit checks and were never affected) to confirm nothing else broke.

**Bug found and fixed by the test suite, not by manual testing:** `AttendanceRecord`'s `date` column was cast as Eloquent's `'date'` type. `AttendanceService::markForClass()` builds `updateOrCreate()`'s search key from a plain `Y-m-d` string, but the `date` cast reformats the value differently when Eloquent serializes it for the actual `INSERT`/`UPDATE`. Search and stored value stopped being byte-identical, so `updateOrCreate` couldn't find the existing row on a second submission and tried to insert a duplicate — caught by `test_resubmitting_the_same_register_updates_rather_than_duplicates` failing with a unique-constraint violation before the fix. Fixed by leaving `date` as a plain string column (no cast) so both sides of the comparison use the same representation. Re-verified live: submitted the same register twice through the actual portal form, second submission correctly updated in place rather than erroring.

## Known deviations from a "textbook" build — and why

- **Database:** MySQL/MariaDB, not PostgreSQL — shared hosting target doesn't offer Postgres (user decision).
- **Queues/cache:** `database` driver, cron-triggered `queue:work --stop-when-empty` — shared host has no confirmed persistent daemons or Redis.
- **Real-time (future):** planned via self-hosted Soketi running in the host's Node.js app slot, once broadcasting is actually wired up (not yet implemented).
- **Storage:** local disk via `Storage` facade abstraction now; S3-compatible swap-in later (user decision).
- **Spatie permission migration was hand-modified**: `model_has_roles`/`model_has_permissions` team_foreign_key columns made nullable (MySQL forbids NULL in a composite primary key, so those became `unique()` indexes instead of `primary()`). This was necessary to represent platform-level (Super Admin, no school) role assignments at all under Spatie's teams feature.
